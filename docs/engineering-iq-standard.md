# Lil' Tueeq Engineering Intelligence Quotient Standard

## Mission

Lil' Tueeq is not being optimized to sound intelligent. He is being engineered to produce unusually strong engineering outcomes under unfamiliarity, ambiguity, failure, limited attempts, and adversarial verification.

Respectability remains the safety floor. Engineering IQ measures capability above that floor.

## Core rule

The agent never grades itself.

Every challenge is bound to:
- an immutable source revision;
- explicit budgets;
- hidden deterministic checks;
- required evidence;
- an authoritative external verdict.

A model claim such as "fixed", "understood", "verified", or "passed" has zero scoring authority.

## Dimensions

1. Architecture reconstruction
2. Causal debugging
3. Invariant discovery
4. System design
5. Concurrency reasoning
6. Security reasoning
7. Recovery reasoning
8. Performance reasoning
9. Transfer learning
10. Self-critique
11. Evidence discipline
12. Implementation accuracy

## Initial benchmark ladder

### EIQ-100 — Local reasoning
Small defects where the correct behavior is fully observable.

### EIQ-200 — Repository comprehension
Multi-file tasks that require architecture reconstruction before editing.

### EIQ-300 — Causal debugging
Several symptoms and plausible causes; only one repair satisfies hidden checks.

### EIQ-400 — Systems engineering
Cross-boundary work spanning storage, concurrency, networking, security, or deployment semantics.

### EIQ-500 — Adversarial engineering
Misleading tests, stale assumptions, hostile inputs, crash windows, and hidden invariants.

### EIQ-600 — Transfer
Unfamiliar libraries/protocols with enough local evidence to infer correct behavior without prior specialization.

### EIQ-700 — Principal-engineer synthesis
Competing architectures with explicit operational, cost, reliability, security, and migration constraints.

### EIQ-800 — Super Geek gauntlet
Large unfamiliar system, incomplete documentation, multiple defects, misleading evidence, concurrent failure, bounded attempts, and hidden end-to-end verification.

## Scoring doctrine

No partial narrative credit for failed hidden invariants.

Track separately:
- correctness;
- causal diagnosis;
- minimality of repair;
- evidence quality;
- regression resistance;
- architectural quality;
- budget efficiency;
- transfer performance.

The objective is not a vanity number. The objective is a capability curve that exposes exactly where Lil' Tueeq stops being exceptional.

## Anti-cheating rules

- No self-reported pass.
- No exposing hidden checks to the reasoning model.
- No changing tests to obtain green.
- No task-specific hardcoding.
- No scoring a known challenge after its solution has been placed in context.
- No silently using a stronger model to rescue weak system architecture.
- No claiming transfer from repeated exposure to the same fixture.

## Development loop

1. Give Tueeq a challenge he has not seen.
2. Preserve immutable starting state.
3. Let him inspect and reason.
4. Require an explicit causal hypothesis before repair on debugging tasks.
5. Let him implement within budget.
6. Run hidden checks outside the model.
7. Record evidence and failure class.
8. Turn every serious failure into a permanent architecture/training target.
9. Re-run on fresh variants, not memorized copies.
10. Raise difficulty until the system breaks again.

## First objective

Build a benchmark pack where a merely competent coding assistant fails for structural reasons, then improve Lil' Tueeq until he passes without weakening the benchmark.
